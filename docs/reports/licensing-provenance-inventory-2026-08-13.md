# Licensing/provenance inventory — 2026-08-13

Status: dated evidence report for #354. This report inventories provenance and repository-role evidence; it **does not choose a license, grant permissions, or make a legal conclusion**.

Base inspected: current `main` at the start of this audit (`12f53777d883510ab2cb133beea7cf15d434b31f`).

## Executive summary

A blanket repository-wide license would currently be misleading without explicit scopes/exceptions. The checkout combines reusable Thestra runtime code, Thestra Studio/editor code, Second Gate authored Project data, game assets with mixed/partly undocumented provenance, third-party fonts, npm/Electron dependencies, an adapted Apache-2.0 agent skill, reference/inspiration material from another game, generated test/build artifacts, and AI/procedural asset-production workflows.

The strongest concrete findings are:

- `package.json` says `"license": "ISC"`, and the root package record in `package-lock.json` repeats `ISC`, but neither file establishes that ISC was deliberately selected for the whole repository. The package is specifically named `second-rite-editor` and points to Electron `main.js`, so this metadata is at least structurally narrower than the repository.
- `package-lock.json` records dependency licenses independently (for example Electron 43.2.0 as MIT and `@electron-internal/extract-zip` as BSD-2-Clause). `node_modules/` is ignored rather than tracked.
- `assets/fonts/` contains many third-party font binaries. Git history explicitly records several Google Fonts additions as OFL and another batch as open-source/OFL, while `JoHandwriting.ttf` appears separately owner-specific. There is no observed aggregate font LICENSE/NOTICE beside the directory, so per-font provenance should not be inferred from tracking alone.
- `.claude/skills/second-rite-blender-modeling/NOTICE.md` is an explicit third-party attribution: it says the skill adapts `terminal-skills` / Andrew1326's `blender-3d-modeling`, identified upstream as Apache-2.0.
- `tools/effekseer/` contains repository-authored integration/build/shim material around the external Effekseer dependency. The build README says `build.ps1` clones/configures Effekseer and produces a gitignored DLL; it also credits `gittup/EffekseerForLove` for the LOVE batch-flush prior art. The generated `effekseer_shim.dll` and provenance sidecar are ignored.
- `tools/asset-gen/` explicitly supports OpenAI/Gemini/OpenRouter and local Stable Diffusion/Forge providers. Its staged `out/` is ignored, and run manifests record prompt, provider, model and target path; promoted outputs can enter `assets/`. Therefore some tracked Project assets may be AI-assisted/generated even when the promotion manifest itself is no longer colocated with the promoted file.
- `assets/models/kit/` has unusually strong procedural provenance: Git history says the kit pieces are deterministically generated by a repository script and texture-map against the existing map atlas. Other model subtrees do not automatically inherit that provenance.
- `inspiration/IMPORTANT.md` explicitly says the entire `inspiration/` tree refers to **another game** used as inspiration and is not this Lua game. That tree is reference/development material, not evidence of redistributable Second Gate content.
- `tools/editor/Assets/icons/thestra-studio/README.md` identifies `icon-32.png` as the canonical authored source, the other PNGs as mechanical nearest-neighbor derivatives, and `.ico`/`.icns` as deterministic generated containers. The generated containers should not be treated as independent authored works/provenance sources.
- `assets/effects/_gate/` is a frozen G5 fixture copied from a real Project effect and its textures. It is tracked verification material, not an independently sourced asset family.

## Inventory by requested category

### 1. Reusable Thestra runtime source

Representative paths: `engine/**`, `presentation/**`, root `main.lua`, runtime-side support currently mixed into `data/` (`data/authored_storage.lua`, `data/json.lua`, `data/loader.lua`, `data/authored_storage_manifest.json`).

Current evidence: AGENTS describes the LÖVE/Lua runtime and its data-driven architecture. #382/PR #383 separately identify `engine/**`, `presentation/**`, `main.lua`, and the four runtime support files in `data/` as runtime-owned rather than Project-owned.

Embedded license/notice evidence: no root `LICENSE`/`COPYING` was present in the inspected tree; no runtime-wide embedded license was found in the targeted provenance pass.

Repository role: shipped/installed runtime source, reusable across Projects. The `data/` support-file exception is a physical-layout problem, not evidence that those Lua files are Second Gate authored data.

Blanket-license hazard: runtime source is semantically distinct from Project-authored data/assets and from third-party dependencies. The existing npm `ISC` field is attached to the Electron package record, not a demonstrated runtime licensing decision.

Owner questions: choose the intended policy for reusable runtime source; decide whether any embedded third-party Lua/source files require separate notices before implementing that policy.

### 2. Thestra Studio/editor/tooling source

Representative paths: root `main.js`, `package.json`, `package-lock.json`, `tools/editor/**`, Studio launcher/icon build code; shared repository tooling under `tools/export/**`, `tools/golden/**`, `tools/delegate/**`, analysis/production scripts where applicable.

Current evidence: `package.json` names `second-rite-editor`, uses Electron as its sole devDependency, and points `main` at root `main.js`. #382/PR #383 classify the Electron host and `tools/editor/**` as Studio-owned while exporter/golden/delegation remain shared development tooling.

Embedded license/notice evidence: `package.json` and root package lock record say ISC, but issue #354 explicitly warns not to assume this was intentional rather than boilerplate. `.claude/skills/second-rite-blender-modeling/NOTICE.md` separately preserves an Apache-2.0 upstream attribution for that adapted skill.

Repository role: Studio is installed authoring application source; much of `tools/**` is development/verification rather than shipped Project content.

Blanket-license hazard: even if ISC is eventually confirmed for the Node/Electron package, that would not by itself establish the policy for runtime, game writing/data, art, references, or third-party material.

Owner questions: confirm whether the current ISC metadata was deliberate for Studio/tooling at all; choose whether reusable Studio and shared development tools share a policy or need separate scopes.

### 3. Second Gate authored game data/writing

Current evidence: AGENTS says content/behavior is authored in `data/*.json`; #382/PR #383 identify authored JSON/fragments as the Second Gate Project side of the current mixed checkout. This is distinct from the runtime Lua/support files currently colocated in `data/`.

Embedded license/notice evidence: none found that grants a repository-wide permission for game data/writing.

Repository role: Project-owned authored content; some documentation is development-facing and need not ship even when game-specific.

Blanket-license hazard: game text/data may embody creative content and product-specific design even though it is machine-readable JSON. Treating all tracked source as one software package would erase this boundary.

Owner questions: choose whether game data/writing follows code policy, an asset/content policy, or another explicit scope; decide what game-specific documentation, if any, is covered versus reference-only.

## Package metadata and dependency boundary

`package.json` is specifically an Electron editor package:

```json
{
  "name": "second-rite-editor",
  "main": "main.js",
  "license": "ISC",
  "devDependencies": { "electron": "^43.2.0" }
}
```

The root package entry in `package-lock.json` repeats ISC. Dependency entries carry their own license metadata. This is evidence of **current metadata**, not evidence that the owner intentionally chose ISC for runtime, Project data, assets, or even Studio itself. Issue #354 explicitly reserves that policy decision to the owner.

## Public-tracking exceptions a future root policy should address explicitly

Without deciding whether these files should be removed, moved, or relicensed, the current public tree contains categories that should be explicitly scoped/excepted rather than silently swept into a root grant:

1. third-party fonts and any other externally sourced assets;
2. `inspiration/**` and similar reference-only material;
3. adapted third-party skill material with its own notice/license;
4. generated/native dependency outputs when distributed;
5. AI-assisted/generated outputs whose provider/model/source provenance differs;
6. named covers or other derivative audio/material;
7. files whose provenance remains unknown after history review.
